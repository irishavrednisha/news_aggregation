# Stage 4 / 7 — самостоятельная сводка Gemma по проверенным фактам

Исходная ветка: `test/stage3-holdout-postgres-2026-11-19`, коммит `4e2e56b`.
Новая ветка: `feat/stage4-grounded-gemma-abstractive-2026-11-19`.
Старый `master` не использовался.

## Статус безопасности

Это **изолированный конвейер абстракативных ЧЕРНОВИКОВ**, а не разрешение
публиковать новости. `main.py process` в ветке этапа 3 по-прежнему защищён
от неявного запуска последующих стадий. Новый CLI **никогда** не меняет
`news.text`, `clusters.summary_text`, `posts.post_text`, `clusters.status`,
решения Telegram-модерации и не отправляет сообщения в MAX.

Даже `summary_draft` означает **только** успешные механические проверки
и самопроверку Gemma, а не доказанную правду. Публикация возможна
только после дальнейшего отдельного подключения к ручной модерации.
`summary_review` означает недостаток источника, проблемы извлечения,
ошибку генерации или провал валидатора.

## Как работает

1. Вход — существующие `News` одного `Cluster`; исходные заголовки,
   URL, тексты и даты сохраняются без изменений.
2. Старый `build_textrank_summary` создаёт **только baseline для сравнения**.
3. Источники сохраняются **целиком без изменения**. Для подготовки
   отдельной рабочей копии скрипт находит повторяющиеся длинные хвостовые
   фрагменты между разными кластерами одного сайта. Сомнительные места
   протоколируются как `source_cleanup_notes`. Источник ошибки сбора
   следует дополнительно исправить в сборщике; очистка не заменяет этого.
4. Факты теперь выделяются **детерминированно, из дословных фрагментов**
   заголовка и начала статьи: `organization/event/object/location/date/number/outcome`.
   Каждый факт содержит `value`, `quote`, `source_id`.
   Эта схема устраняет необходимость просить Gemma придумывать строковые
   цитаты; обязательны реально обнаруженное событие и минимум 3 факта.
   Статьи-обзоры без установленного события идут в `summary_review`.
5. Gemma пишет **новую связанную новость целиком** по структурированным
   фактам и кратким первоисточникам: 3–5 предложений, до 800 символов.
6. Отдельный `abstractive_validator.py` проверяет названия, аббревиатуры,
   числа и контексты единиц измерения, месяцы, имена, модальность
   «план / выполнено», отрицания, направление изменения, новые причины,
   повторяющиеся предложения и дословные совпадения.
7. Вторая генерация Gemma выполняет проверку каждого предложения по
   цитатам. Это **не независимая экспертная оценка**: даже результат
   `supported` не гарантирует истинность. Неподтверждённые цитаты
   и неопределённость блокируют черновик.
8. При сбое — до двух повторных попыток (всего максимум 3). Все версии
   и замечания остаются в отчёте. Никакого текстового fallback,
   готового к публикации, не существует.

Модель: Ollama на `http://127.0.0.1:11434/api/chat` через уже существующий
`processing.extractive_rewriter.ollama_rewrite`. Облачные модели
и произвольные теги запрещены. Параметры `temperature=0`,
`num_ctx=4096`, `num_predict=1024`.
По умолчанию `gemma3:4b`: подходит как стартовый квантованный 4B
вариант для RTX 5060 Ti 8 ГБ; реальное потребление VRAM проверяется
локально, а не предполагается. Для диагностики допустимы `gemma3:1b`
и `gemma2:2b` (качество может быть хуже). Обучение не запускается.

## Windows PowerShell — запуск

Работать из вашей существующей рабочей папки; активация venv не нужна.

```powershell
cd D:\Projects\news_aggregation
git fetch origin
git switch --track origin/feat/stage4-grounded-gemma-abstractive-2026-11-19

# Проверить модель и сервис (при необходимости: ollama pull gemma3:4b)
ollama list
ollama pull gemma3:4b
ollama ps

# Прогнать независимые тесты без GPU
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_stage4_abstractive.py" -v

# Короткий локальный пробник: БД читается, только JSON записывается
.\.venv\Scripts\python.exe scripts\run_stage4_summaries.py --limit 3 --min-clusters 1 --output collector_test_results\stage4_smoke.json

# Основная проверка на 100 НАСТОЯЩИХ кластерах PostgreSQL
.\.venv\Scripts\python.exe scripts\run_stage4_summaries.py --limit 100 --min-clusters 100 --output collector_test_results\stage4_abstractive_100.json
```

Если используете новый локальный каталог и ещё нет настроенного `.venv`,
сначала настройте Python 3.11 и зависимости проекта. Не переустанавливайте
рабочую CUDA/Unsloth-среду ради этих тестов: Gemma запускается через
отдельный Ollama.

**Важно:** скрипт читает вашу PostgreSQL из настроек `config.py`.
При отсутствии 100 кластеров он оставляет реальный частичный JSON,
пишет `minimum_sample_met: false` и завершает команду с кодом 2.
Никакого заполнения выборки синтетическими новостями нет.

Отчёт сохраняется после **каждого** кластера, чтобы при перерыве
длинного локального прогона уже обработанные результаты не пропали.
Чтобы после прерывания не пересчитывать уже проверенные записи, добавьте
к исходной команде **`--resume`** и укажите тот же `--output`.
Скрипт повторно использует только строки с той же моделью и тем же
SHA-256 исходных материалов; изменившиеся источники пересчитываются.
Для повторного измерения качества после изменений промпта/валидатора
используйте **новый JSON-файл без `--resume`**.

## Дополнительное сохранение в PostgreSQL

По умолчанию CLI **не пишет в БД** и сохраняет всё в JSON. Чтобы
дополнительно включить **append-only** журнал `summary_runs`, сначала
сделайте резервную копию БД и примените миграцию:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe scripts\run_stage4_summaries.py --limit 100 --min-clusters 100 --persist --output collector_test_results\stage4_saved_100.json
```

В `summary_runs` отдельно пишутся полные исходные тексты, факты с
цитатами, baseline TextRank, результат Gemma, тег модели и параметры,
каждая попытка, результат валидации и итоговый статус.
История добавляется новыми строками, одобренные `Post` не изменяются.
Нужна актуальная миграция `20261119_04`, которая добавляет только
отдельную таблицу и индексы.

## Оценка качества и критерий завершения

Файл содержит `clusters[]` с оригинальными текстами, фактами, baseline,
новым текстом, всеми замечаниями и повторами; `metrics` с частотой
успешного прохождения валидатора, длиной, копированием предложений,
повторами, сходством с TextRank и грубым прокси длины предложений;
`representative_before_after` до 10 примеров.

**Автоматическая доля `summary_draft` не является точностью фактов.**
`manual_factual_accuracy`, `manual_readability` и
`manual_event_coverage` намеренно равны `null`, пока по 100 независимым
реальным кластерам не проведена ручная проверка.
Примеры «было / стало» формируются программой из результатов, не
сочиняются вручную ради отчёта.

До завершения этапа обязательны:
- Прогон не менее 100 **реальных кластеров** с локальной Gemma.
- Просмотр всех обнаруженных ошибок и особенно ложных пропусков в
  механической проверке.
- Отдельная человеческая разметка фактической точности, читаемости,
  повторов, неинформативных текстов и текстового заимствования.
- Исправление промпта/валидатора по ошибкам и **повторный** замер,
  в том числе на независимой выборке.
- Проверка ограничений памяти и скорости на вашем ПК.

## Известные ограничения

- Валидатор не является полноценной моделью логического вывода;
  слова с разным смыслом, неправильные связи субъект–действие,
  тонкие отрицания и плохо распознанные сущности могут пройти.
- Вторая проверка той же Gemma может разделять её ошибку. Даже
  механически «чистые» материалы должны пройти ручную редактуру.
- В 4096-токенном контексте обрабатываются отобранные фрагменты
  максимум пяти материалов; детали, лежащие дальше, могут быть
  пропущены. Полные оригиналы остаются в отчёте и базе.
- Попадание в `summary_review` не приводит к автоматической
  публикации TextRank. Черновики `summary_draft` также не переводятся
  в `Cluster.ready` без следующего редакционного этапа.

## Исправления после первого прогона 100 реальных кластеров

Файл `stage4_abstractive_100.json` (первый прогон, 19.11.2026)
показал `summary_draft: 1`, `summary_review: 99`, до генерации
дошли только две новости. Среди причин: 13 ошибок JSON-извлечения,
39 пропусков подтверждённого события, несколько сотен отклонённых
Gemma-цитат, которые не являлись точными фрагментами исходника.
У источника НедраДВ наблюдаются фрагменты других новостей внутри
текстов статей.

Важное исправление: **Gemma больше НЕ отвечает за копирование
дословных фактов**. Прямые свидетельства выбирает код, а Gemma
пишет новую связанную сводку целиком и проводит дополнительную
самопроверку, которая не считается независимым доказательством точности. Подозрительные рекламные
или обзорные материалы без события уходят в ручную очередь.

Предварительный **офлайн** аудит подготовки фактов можно повторить
без Ollama, БД и GPU:

```powershell
.\.venv\Scripts\python.exe scripts\audit_stage4_preflight.py --input collector_test_results\stage4_abstractive_100.json --output collector_test_results\stage4_preflight_v2.json
```

Сравнение текста новой модели с **теми же самыми 100 реальными
исходниками** без изменения локальной PostgreSQL и без новых статей:

```powershell
git switch feat/stage4-grounded-gemma-abstractive-2026-11-19
git pull --ff-only origin feat/stage4-grounded-gemma-abstractive-2026-11-19
.\.venv\Scripts\python.exe scripts\run_stage4_summaries.py --input-json collector_test_results\stage4_abstractive_100.json --limit 100 --min-clusters 100 --output collector_test_results\stage4_abstractive_v2_100.json
```

Это **новый результат**: не используйте `--resume` с файлом первого
прогона, так как схема и конвейер изменились. Если новый прогон
прервётся, продолжайте только его с `--resume` и тем же новым путём.

`stage4_preflight_v2.json` оценивает лишь полноту структурирования
буквальных фрагментов. Он **не** измеряет точность Gemma,
читабельность, корректность субъектно-объектных связей или
отсутствие фактических искажений. Этап нельзя объявить
завершённым без повторных реальных сводок и человеческой проверки.

Реальный повторный прогон на тех же 100 источниках показал:
- `summary_draft = 15`, `summary_review = 85`;
- `model_generation_attempted = 80` (ранее 2);
- `source_cleanup_clusters = 25`;
- `no_supported_news_event = 16`;
- из 65 отклонённых после генерации: **34** только из-за семантической
  самопроверки и **31** из-за лексических/структурных правил.

Важные качественные находки:
- № 71: заголовок **«завершается посев»** был превращён моделью в
  **«завершила посев»**, несмотря на `summary_draft`.
- № 50: прогноз Минфина модель превратила в уже зафиксированный доход
  (этот случай был отклонён).
- № 35: одобренный текст содержит неграмотные конструкции
  «XII Соглашение на годы» и «социальный партнерство».
- № 102: `Гиредмета` → `Гиредметом` воспринималось старым
  словарным сопоставлением как новая организация.
- № 32: реклама скидок на АЗС получила `summary_draft`,
  поэтому тематический фильтр и ручная модерация остаются обязательными.
- №№ 105/104: после усечения повторяющегося мусорного хвоста
  оставалась ещё одна соседняя новость; теперь проверяется **один-два**
  предшествующих предложения по независимому совпадению в другом кластере.

### Версия v3 после реальных ошибок

1. `processing/stage4_verification.py` собирает дословные пронумерованные
   фрагменты `source_evidence` из реальных источников и выделенных фактов.
   Модель ссылается на `evidence_ids`, может дать несколько ссылок на
   одно предложение. Код не позволяет подменить цитаты, проверяет
   идентификаторы, числовые утверждения и тематическое пересечение.
2. При оценке каждого предложения Gemma получает уже готовый
   `sentence_id`; ей **не нужно переписывать сам текст предложения**.
3. Проверяются грамматические формы одного названия, не снимая запрета
   на новые имена.
4. Добавлены отдельные защитные правила для
   `main_event_ongoing_changed_to_completed` и
   `forecast_changed_to_observed_result`.
5. Расширен словарь явно выраженных промышленных событий, исправлена
   ложная классификация «Налоги **как** инструмент» как how-to, и
   исправлена цитата года, обрезавшая цифры.

Это **исправления на уровне кода и регрессионных тестов**.
Их фактическое влияние на прохождение 100 реальных статей
с локальной Gemma ещё не измерено.
